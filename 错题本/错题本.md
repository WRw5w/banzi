🏃‍♂️ 3. 搜索与遍历 (DFS / BFS) 的夺命陷阱

无向树 DFS 忘记判父亲
致命点：由于无向连通，儿子会沿着反向边遍历回父亲，导致死循环。
对策：传参必须带上父亲 void dfs(int u, int fa)，并在循环里加上 if(v == fa) continue;。

BFS 标记 vis 的时机错了（极其容易 TLE！）
致命点：在节点出队的时候才标记 vis = true。这会导致同一个节点在队列里被重复塞入多次（如果有多个邻居都指向它），队列瞬间爆炸，空间内存和时间双重超限 (MLE + TLE)。
对策：BFS 必须在节点入队的那一瞬间（或者说压入队列的同时）立刻标记 vis[v] = true。

递归状态恢复（回溯）搞错
致命点：DFS 找所有路径时，vis[u] = 1 之后，在 return 之前忘记 vis[u] = 0，导致其他路径再也走不到这个点了。
🗺️ 4. 最短路算法 (Dijkstra / Floyd / SPFA)

Dijkstra 没加 vis 判重（直接 TLE）
致命点：用 priority_queue 写 Dijkstra 时，出队后没有写 if(vis[u]) continue;。同一个节点以不同的距离多次入队，被处理了无数次。

Dijkstra 处理负权边（WA）
致命点：如果图中有负权边，Dijkstra 的贪心策略直接失效，必须用 Bellman-Ford 或 SPFA。（另外，别信 SPFA，2026年了，只要没负权边，出题人一定会卡死 SPFA，老老实实写 Dijkstra）。

Floyd 初始化错误
致命点：dp 数组没有初始化为极大值，或者忘记初始化对角线 dp[i][i] = 0。
对策：外层必须是 k（中转点），而且是 k, i, j 的循环顺序，写错成 i, j, k 会直接 WA 掉。

极大概率的 inf 溢出（WA）
致命点：你定义了 const long long inf = 2e18;，在最短路松弛操作 if(dist[v] > dist[u] + w) 中，如果 dist[u] 是 inf，加上一个正数 w 会直接爆 long long 变成负数，反而更新了最短路！
对策：防溢出可以写 if(dist[u] != inf && dist[v] > dist[u] + w)。

1. 状态定义与初始化的“幽灵陷阱”

初始化求极值时的 0 与 inf
致命逻辑：求最大值时，把 dp 数组全初始化为 0。

修正：求最大值必须初始化为 -inf（如 -1e18），求最小值必须初始化为 inf。记住：dp[0]（起始状态）通常要有特殊的合法初始值（如 0）！

🔄 2. 遍历顺序的“时间穿越”

区间 DP 的循环顺序灾难
致命逻辑：写区间 DP（如石子合并）时，直接用普通的 for L=1...n 和 for R=L...n。
真相：当你计算 dp[L][R] 时，它需要用到子区间 dp[L+1][R] 的值。但是按照你的循环顺序，dp[L+1][R] 还没被算出来！你拿了一个全是 0 的未来状态在转移。
修正：区间 DP 最外层循环必须是区间长度 len，内层循环是左端点 L，再推导出右端点 R。

🔢 3. 状态转移的“漏网之鱼”

只考虑了转移，忘记了“白手起家”
致命逻辑：写最长上升子序列（LIS）时，只写了 dp[i] = max(dp[j] + 1)，结果跑出来全是 0。
真相：每个元素都可以不依赖前面的元素，单独成为一个长度为 1 的合法状态。
修正：初始化时必须把每个 dp[i] 设为 1，或者转移时加上 dp[i] = max(dp[i], 1)。

容斥原理（计数 DP）中的重复计算
致命逻辑：在二维网格走迷宫求方案数时，有障碍物。你算“经过某个障碍物”的方案数，把两个不同的障碍物当成了独立事件减去。
真相：如果一条路径同时经过了障碍物 A 和 B，你把它减了两次！
修正：计数类 DP 如果有多个否定条件，大概率要用容斥原理（加奇减偶），或者强制规定**“第一次”**碰到障碍物的状态来做到不重不漏。

💣 4. 边界与越界（极易 RE / WA）

负数下标越界
致命逻辑：转移方程里有 dp[i-2]，直接放在 for i=1...n 里面跑。
真相：当 i=1 时，访问 dp[-1]，C++ 不会立刻报错，而是会读取内存里的乱码，导致极难复现的随机 WA。
修正：涉及 i-2 的转移，循环必须从 i=2 或 i=3 开始，并且手动在外面把 i=1 和 i=2 的 Base Case 写死。

致命逻辑：dp[j] = dp[j - weight[i]] + value[i]。
真相：如果当前容量 j 比 weight[i] 小，j - weight[i] 会变成负数，越界。
修正：内层循环的容量 j 必须保证 j >= weight[i]（比如把循环下限设为 weight[i]）。

🧱 1. 数据结构（DSU / 线段树）的底层逻辑崩塌
🟢 并查集（DSU）的致命手误

“假合并”（最经典的逻辑 WA）
致命逻辑：合并两个集合时，写成了 fa[u] = v; 或者 fa[find(u)] = v;。
真相：你只是把 u 这个点或者 u 的根节点接到了 v 的下面，但并没有接到 v 的根节点下面！这会导致集合变成极其扭曲的形态。
修正：合并操作永远永远写成：fa[find(u)] = find(v);（必须是根节点合并根节点）。

初始化遗忘（本地 AC，提交 WA）
致命逻辑：定义了 int fa[N]，然后直接开始 union。
真相：fa 数组默认全是 0，所有的点从一开始就被认为是在同一个集合（0的集合）里！
修正：solve() 开头第一件事就是 iota(fa + 1, fa + n + 1, 1); 或者 for(int i=1; i<=n; i++) fa[i] = i;。

判断连通块数量的错觉
致命逻辑：用 set 收集所有的 fa[i] 来统计有几个连通块。
真相：如果没有发生路径压缩，fa[i] 只是它的直接父亲，不一定是根！
修正：必须收集 find(i) 的种类数；或者直接统计 if (fa[i] == i) 的个数，等于根的数量，也就是连通块的数量。
🌲 线段树（Segment Tree）的夺命连环坑

Lazy Tag 的“覆盖”与“累加”混淆
致命逻辑：区间加法（Add）时，下传标记写成了 tag[ls] = tag[u];。
真相：如果是区间加法，多次操作累加，标记必须是 tag[ls] += tag[u];！只有“区间赋值（Assign）”操作才是直接覆盖 =。

下传标记（Pushdown）时没更新子节点的值
致命逻辑：pushdown 函数里只写了 tag[ls] += tag[u]，忘记写 tree[ls] += ...。
真相：打标记的同时，必须同步更新子节点本身的答案值！否则查询时查不到正确答案。
修正：pushdown 里的标准动作是：1. 传标记给儿子；2. 用标记更新儿子的 tree 值；3. 清空父亲的标记 tag[u] = 0。

区间交集的长度算错
致命逻辑：区间加上一个值 val 时，子节点的和应该增加 val * 区间长度。你把左儿子的区间长度写成了 mid - L + 1，但 L 是当前查询的左边界，不是线段树节点的左边界！
修正：必须用线段树节点原本的控制范围 l 和 r。左儿子长度永远是 mid - l + 1，右儿子长度永远是 r - mid。

build() 和 query() 的越界返回
致命逻辑：求区间最大值，query 遇到不相交的区间 return 0;。
真相：如果原数组全是负数，你 return 0 直接把正确答案覆盖了！
修正：求最大值越界返回 -inf，求最小值返回 inf，求和返回 0。
🔍 2. 二分与双指针（Binary Search & Two Pointers）
⚖️ 二分查找（Binary Search）的“死循环”与“溢出”

死循环魔咒（mid 取偏了）
致命逻辑：写出了 while(l < r) { mid = (l + r) / 2; if(...) l = mid; else r = mid - 1; }。
真相：当 l 和 r 只差 1 的时候（比如 l=3, r=4），mid = (3+4)/2 = 3。如果你走到 l = mid 分支，l 还是 3，区间变成了 [3, 4]，无限死循环 TLE！
修正口诀：只要出现了 l = mid，上面算 mid 就必须加上 1，即 mid = (l + r + 1) / 2。 如果是 r = mid，则用 mid = (l + r) / 2。

🏃‍♂️ 双指针（Two Pointers / Sliding Window）的收尾灾难

致命逻辑：当不满足条件时，一直移动左指针 while(sum > K) { sum -= a[l++]; }。
真相：如果整个数组所有的数都极其大（比如 a[i] > K 永远成立），l 会一直加，直到超过了 r，导致区间长度变成负数，甚至越界读取乱码！
